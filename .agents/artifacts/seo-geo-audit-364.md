## @research brief

**Question:** SEO + GEO audit of the public docs site after the #361/PR #362 restructure — what discoverability work is worth filing as `@dev`/`@design` issues, and in what order.

### TL;DR
Recommend **(c)**, but scoped narrow: fix a handful of cheap, real classic-SEO gaps (structured-data completeness, a missing canonical, an oversized meta description), and do the one clearly-evidenced GEO tightening (stating cost/identity claims more explicitly and matching them in structured data). Do **not** chase `llms.txt` or further FAQ-schema engineering — the best available measured evidence says neither pays off. Two things that look like gaps are not fixable from this repo at all (robots.txt scope, HTTPS enforcement is a Pages setting, not a file) and one thing that looks broken (the `model.html` redirect stub) is already close to the best achievable given GitHub Pages legacy builds. Confidence: medium-high on SEO findings (directly measured against served bytes); medium on GEO findings (grounded in a small number of primary/measured sources, with explicit gaps noted below).

### Findings — SEO

- **[high] `SoftwareApplication` JSON-LD in `docs/index.html` is missing Google's required `offers` (and `aggregateRating`/`review`) properties, so it is not eligible for the SoftwareApplication rich result at all.** Measured on the live page (fetched `https://alexandre.machado.cc/audio-blackbox/`, lines 30-48 of the served HTML): the block has `name`, `url`, `description`, `applicationCategory`, `operatingSystem`, `author`, `license`, `sameAs` — no `offers`, no `aggregateRating`. Google Search Central, *Software App | Google Search Central*, https://developers.google.com/search/docs/appearance/structured-data/software-app — fetched summary: "`offers.price`: 'An offer to sell the app' (must be included)... Rating or review: Must include either `aggregateRating` or `review`... Free apps should set `offers.price` to `0`." Fix: add `"offers": {"@type": "Offer", "price": "0", "priceCurrency": "USD"}` to the existing `SoftwareApplication` block in `docs/index.html`. Do **not** fabricate an `aggregateRating` — there is no real one; accept the type stays ineligible for a rich *rating* snippet until a real Play Store rating exists to cite.

- **[medium] `docs/design/index.html` (Living Design Model) has zero page-level SEO metadata beyond `<title>` and a meta description: no `<link rel="canonical">`, no Open Graph/Twitter tags, no structured data.** Measured on the live page (fetched `https://alexandre.machado.cc/audio-blackbox/design/`, grep for `canonical|og:|twitter:|application/ld` returned nothing outside a code comment). This page is listed in `docs/sitemap.xml` with `priority 0.5`, i.e. deliberately meant to be indexed, so the missing self-canonical is a real gap (no defense against `?query`/trailing-slash URL variants splitting signal). Fix: add `<link rel="canonical" href="https://alexandre.machado.cc/audio-blackbox/design/">` to the `<head>` of `docs/design/index.html`.

- **[medium] The meta description on `docs/index.html` is long enough to be truncated in search snippets.** Measured on the live page: `<meta name="description" content="A continuous audio recorder for Android that works like a flight recorder / dashcam: holds up to the last 45 minutes in RAM, writes to storage only when you ask it to. 100% Private, Zero Network Egress.">` — roughly 205 characters. Google Search Central, *Control your snippets*, https://developers.google.com/search/docs/appearance/snippet — fetched: "There's no limit on how long a meta description can be, but the snippet is truncated in Google Search results as needed, typically to fit the device width." No hard rule violated, but the practical convention (~155-160 chars before common truncation) is exceeded, so the strongest claim risks being cut. Fix: shorten the `<meta name="description">` in `docs/index.html` to front-load the unique value proposition within ~155 characters. Note: this description currently also carries the "45 minutes" figure tracked under #363 for accuracy — rewriting it is a natural place to fix both at once, but the length problem exists independent of that number's accuracy.

- **[nit] `<title>` and `og:title`/`twitter:title` on `docs/index.html` use slightly different wording** ("Continuous **Ambient** Audio Buffer" vs. "Continuous Audio Buffer"). Measured on the live page, lines 6 and 17-18/26. Fix: make `og:title`/`twitter:title` match `<title>` verbatim in `docs/index.html`.

- **[not worth filing — the FAQ schema's target rich-result surface is fully retired, independent of markup quality] `FAQPage` JSON-LD on `docs/index.html` targets a Google Search feature that no longer exists.** Google's FAQ rich results were restricted to authoritative government/health sites in Aug 2023 and then fully deprecated: Search Engine Journal, *Google Drops FAQ Rich Results From Search*, https://www.searchenginejournal.com/google-drops-faq-rich-results-from-search/574429/ — fetched, quoting Google's own notice: "FAQ rich results are no longer appearing in Google Search. We will be dropping the FAQ search appearance, rich result report, and support in the Rich results test in June 2026." (secondary source quoting a primary Google announcement I could not load directly — `developers.google.com/search/blog/2023/08/howto-faq-changes` returned only a truncated archive listing when fetched). No classic-SEO benefit remains available from this markup regardless of how it's tuned; leave it as-is (it costs nothing and mirrors visible content) but do not invest further engineering in it for search-snippet purposes. (Its GEO value is a separate, weaker-evidenced question — see GEO findings.)

- **[informational, not fixable from this repo] `/audio-blackbox/robots.txt` 404s (confirmed, matches `@sre`'s finding) — but this does not mean crawl access is unrestricted at the origin, and it cannot be fixed by adding a file under `docs/`.** Google Search Central, *How to write and submit a robots.txt file*, https://developers.google.com/search/docs/crawling-indexing/robots/create-robots-txt — fetched: "The robots.txt file must be located at the root of the site host... A robots.txt file applies only to paths within the protocol, host, and port where it is posted... It cannot be placed in a subdirectory." I fetched `https://alexandre.machado.cc/robots.txt` (the actual origin root, not the project path) directly: it returns 200 with `User-agent: *` / `Allow: /`, i.e. it is the one robots.txt that governs the whole origin including `/audio-blackbox/*`, and it permits everything. A `docs/robots.txt` in this repo would only ever be reachable at `/audio-blackbox/robots.txt`, a URL no crawler consults per the spec above — so there is no actionable fix here at all, and no crawl-access problem either.

- **[medium, cross-repo — not an `@dev`/`@design` issue against this repo unless the same repo owns the apex] The origin's actual robots.txt does not reference this project's sitemap.** Measured: the fetched apex `robots.txt` contains only `Sitemap: https://alexandre.machado.cc/sitemap.xml`, never `https://alexandre.machado.cc/audio-blackbox/sitemap.xml`. Discovery of `docs/sitemap.xml` therefore depends on the `<link rel="sitemap">` hint in `docs/index.html` (non-standard, not honored by major crawlers) and/or a manual Search Console submission, not on the robots.txt convention. Whoever owns the apex-domain repo should add a second `Sitemap:` line; flag this to the operator as a cross-repo follow-up rather than filing it against `audio-blackbox`.

- **[nit, ops setting not a file change] `https_enforced: false` confirmed independently: `curl` to `http://alexandre.machado.cc/audio-blackbox/` returns `200` directly, no redirect to `https://`.** This is a GitHub repo Settings → Pages → "Enforce HTTPS" checkbox, not a change to any file in `docs/`. Since the issue states the HTTPS cert is already approved, flipping the toggle should be low-risk. File as an ops/settings task, not a code issue.

- **[no action needed — already close to the best achievable] `docs/design/model.html`'s meta-refresh redirect (`content="0; url=./"` plus a correct `<link rel="canonical">` to `/design/`) is the documented best-practice substitute for a 301 on a platform that can't serve one.** Measured on the live page (fetched, 14 lines, clean): instant (0-second) refresh + matching canonical, exactly as recommended. Google Search Central, *Tell Google about redirects*, https://developers.google.com/search/docs/crawling-indexing/301-redirects — fetched: "If server-side redirects aren't possible to implement on your platform, meta refresh redirects may be a viable alternative... Google treats [an instant, 0-second] meta refresh as [a] permanent redirect," while delayed ones are treated as temporary. GitHub Pages legacy builds cannot serve a real 301, so this is the correct implementation already; no fix to recommend.

- **Not flagged as findings (checked, no issue found):** viewport meta tag present and correct on both pages (measured); heading hierarchy on `docs/index.html` is a single `<h1>` followed by properly nested `<h2>`/`<h3>` (measured, `grep` of heading tags); all 5 `<img>` tags across `docs/index.html` carry descriptive `alt` text (measured); `docs/sitemap.xml`'s two `<loc>` entries both resolve 200 live and `lastmod` dates are recent/plausible (measured); cross-linking between the hotsite and the design page is present in both directions (measured).

- **Judgment call for the operator, not resolved here: should `docs/design/index.html` be `noindex`?** The page is already deliberately listed in `sitemap.xml` at `priority 0.5`, which is a clear existing signal the owner wants it indexed. Nothing found in this audit argues strongly either way (it's a legitimate, unique, developer/design-facing document, not thin or duplicate content). Recommendation: keep it indexed and just close the hygiene gap (canonical tag, above) rather than `noindex`-ing it.

### Findings — GEO

- **[measured, own crawl — informational, no fix needed] LLM-crawler access is not actually restricted.** The same origin-root `robots.txt` found above (`User-agent: *` / `Allow: /`, no bot-specific block) governs GPTBot, Google-Extended, PerplexityBot, ClaudeBot, etc. as well as classic search crawlers, since there is no separate allowance mechanism for AI user-agents in the robots.txt spec beyond per-user-agent blocks, which are absent here. The "no `robots.txt` at `/audio-blackbox/`" framing in the dispatch does not translate into a real GEO-crawl-access problem — see the SEO robots.txt finding above for the citation and full reasoning; it applies identically here.

- **[reported/measured on the live page, medium] The hotsite states identity, platform, capability and privacy posture as extractable self-contained prose within a single page, but states cost only inside one FAQ answer, not in the main body or in structured data.** Measured: the "What is Audio Blackbox?" section (fetched page, lines 1103-1115) states what the app is, its platform-independent value proposition, and its no-`INTERNET`-permission privacy posture in three self-contained paragraphs. Cost/pricing appears only in FAQ item 4 ("Is Audio Blackbox free and open source? ... Yes... GNU General Public License v3.0") and is entirely absent from the `SoftwareApplication` JSON-LD (no `offers`, see SEO finding above). An answer engine extracting only the main-body prose (not the FAQ) would have no cost claim to cite. Fix: add one explicit cost/status sentence to the main hero or "What is Audio Blackbox?" copy (e.g., "free and open-source, currently in open beta"), and add `offers.price=0` to the JSON-LD (same fix as the SEO finding — this is one fix serving both).

- **[reported, primary/measured — do not implement] `llms.txt` has no demonstrated GEO payoff and is not confirmed to be consumed by any major LLM provider's retrieval/answer pipeline.** Ahrefs, *We Analyzed 137K Sites: 97% of llms.txt Files Never Get Read*, https://ahrefs.com/blog/llmstxt-study/ — fetched: methodology analyzed 137,210 domains via Ahrefs' own bot/traffic logs (May 2026); "28% of analyzed domains... published llms.txt files... 97% of those files received zero requests... AI retrieval bots... accounted for just 1.1% of requests," concluding "If your goal is showing up in ChatGPT, Perplexity, or AI Overviews, an llms.txt file is largely decoration." Separately, llmstxt.org (the spec itself, https://llmstxt.org/, fetched) confirms adoption is currently limited to AI labs publishing *their own* llms.txt for *their own developer docs* (OpenAI, Anthropic, Gemini) — this is evidence the format exists and labs know about it, not evidence that any lab's *crawler* consumes third-party llms.txt files when visiting other sites. No official confirmation from OpenAI, Anthropic, or Google that their crawlers read `llms.txt` was found. Recommendation: do not file an `llms.txt` issue; this is a case where "insufficient/negative public evidence" is itself the actionable answer.

- **[speculative/weak evidence — vendor-sourced, mark accordingly] FAQ-shaped Q/A structure (with or without schema) is commonly claimed by GEO-focused vendor content to help LLM answer-extraction via clean "chunking," but I could not find a primary benchmark isolating the *schema markup itself* (as opposed to well-structured visible Q/A prose) as the causal factor.** The one primary academic source I could fetch, Aggarwal et al., *GEO: Generative Engine Optimization*, arXiv:2311.09735, https://arxiv.org/abs/2311.09735 (abstract fetched) — states only that "GEO can boost visibility by up to 40% in generative engine responses" and that "efficacy... varies across domains," without the abstract itself enumerating which specific tactics (quotations, statistics, structured markup) drove that number; I did not fetch the full paper body within the timebox, so I cannot confirm or deny the more specific "statistics/quotations beat keyword stuffing" claim that secondary blog summaries attribute to this paper. Given the FAQPage schema here already mirrors real, visible FAQ content verbatim (confirmed on read) rather than being schema-only cruft, there is no indicated problem to fix — but also no strong evidence that further engineering the schema (vs. just keeping the visible FAQ good) would move an LLM-citation outcome. Recommendation: leave as-is, don't invest further.

- **Not found within timebox: any published benchmark measuring the marginal GEO effect of adding `offers`/`aggregateRating` to structured data, or of self-contained-claim density, specifically for a small independent-developer site (as opposed to enterprise SEO case studies).** This sub-question is answered here as **insufficient public evidence** rather than papered over.

### Implications for the decision

- **(a) do nothing** is not supported: the `offers`-missing schema and the design page's missing canonical are free, mechanical fixes with a clear standards citation each; leaving them costs nothing to fix and nothing to lose by fixing.
- **(b) classic-SEO hygiene** is worth doing in full — it's cheap and every item above has a named file and a concrete change.
- **(c) GEO-specific work** is worth doing *narrowly*: tighten the cost claim (one sentence + one JSON-LD property) since that's the one place the evidence points to a real gap. Do **not** add `llms.txt` (negative measured evidence) and don't invest further in FAQ-schema tuning (no isolated evidence it matters beyond what's already shipped).

**Suggested filing order** (all as `@design`/`@dev` issues against `audio-blackbox` unless noted):
1. **High** — add `offers` (price 0) to the `SoftwareApplication` JSON-LD in `docs/index.html` (also serves the GEO cost-clarity finding — one fix, two findings).
2. **Medium** — add `<link rel="canonical">` to `docs/design/index.html`.
3. **Medium** — shorten `docs/index.html`'s meta description to front-load the value prop within ~155 characters (coordinate with whoever picks up #363, since the current text also carries the retention figure being revised there).
4. **Medium** — add one explicit "free / open beta" cost sentence to the hotsite's main body copy (not just the FAQ).
5. **Nit** — sync `og:title`/`twitter:title` with `<title>` in `docs/index.html`.
6. **Ops setting, not a filed code issue** — enable "Enforce HTTPS" in GitHub repo Settings → Pages.
7. **Cross-repo note, not a code issue here** — tell whoever owns the apex-domain repo that its `robots.txt` should add a `Sitemap:` line for `https://alexandre.machado.cc/audio-blackbox/sitemap.xml`.
8. **Explicitly not worth doing:** `llms.txt`, further FAQ-schema engineering, any `docs/robots.txt` file, and any change to `docs/design/model.html`'s redirect mechanism (already the documented best-achievable pattern).

### Coverage & gaps
- **Searched:** Google FAQ rich results deprecation timeline; llms.txt adoption/consumption evidence; GEO/generative-engine-optimization academic benchmarks; Google robots.txt file-location spec; Google redirect guidance (meta refresh vs. 301); Google structured-data requirements for SoftwareApplication; Google meta-description/snippet guidance; schema.org SoftwareApplication property definitions.
- **Read (fetched):** the four live URLs given (`docs/index.html`, `docs/design/index.html`, `docs/design/model.html` incl. response headers, `docs/sitemap.xml`); the live origin-root `robots.txt` and the live `/audio-blackbox/robots.txt` and `/audio-blackbox/llms.txt` (both 404, confirmed); a plain `http://` request to confirm no HTTPS redirect; developers.google.com structured-data docs (software-app), snippet-control docs, robots.txt creation docs, 301-redirect docs; schema.org/SoftwareApplication; Search Engine Journal's report of Google's FAQ deprecation notice; llmstxt.org; Ahrefs' 137K-domain llms.txt study; the arXiv abstract of the Princeton GEO paper. 16 sources total.
- **NOT found / could not establish:** the exact tactic-level breakdown behind the Princeton GEO paper's "40% visibility boost" figure (abstract only, full paper not fetched within timebox — flagged above as insufficient); any primary source directly confirming Google's original Aug-2023 FAQ-restriction blog post's exact wording (that specific `developers.google.com` URL returned only a truncated archive listing when fetched; the deprecation-to-zero fact for 2026 is corroborated by a secondary source quoting Google directly, which I judge sufficient for the finding but weaker than a direct primary fetch); any benchmark isolating structured-data completeness or self-contained-claim density as a causal GEO factor for a small site.
- **Staleness/bias notes:** the Ahrefs llms.txt study and the SEO-vendor summaries surfaced by search are vendor-authored (Ahrefs, Search Engine Journal, Search Engine Land, etc.) — I treated the Ahrefs piece as the strongest available evidence because it discloses its own measured methodology (137K domains, own bot logs) rather than asserting an opinion, but it is still a vendor's own study, not peer-reviewed. The Princeton GEO paper is the one genuinely independent academic source used, and even there I only verified the abstract, not the full methodology — that gap is stated above rather than filled in from memory.
