## Research brief: exact off-page steps to get the hotsite indexed and cited by search + AI engines

**TL;DR** — Ordered checklist. All of these are safe to do; none conflicts with the beta/GPL status.

1. *(owner action)* In Google Search Console, add a **URL-prefix property** for `https://alexandre.machado.cc/audio-blackbox/` — not a Domain property (that would require a DNS TXT record on `machado.cc`, which is a different concern than this repo, and buys nothing extra for a single sub-path site). Verify via HTML meta-tag or the GA/GTM method if either is already wired into `docs/`.
2. *(owner action)* Once #283's `docs/sitemap.xml` ships, submit `https://alexandre.machado.cc/audio-blackbox/sitemap.xml` directly in that GSC property's "Sitemaps" panel — this bypasses the "sitemap only covers its own subtree" limitation entirely, and the subtree limitation doesn't hurt you anyway since every page you own is under `/audio-blackbox/`.
3. *(owner action)* In Bing Webmaster Tools, use **"Import from Google Search Console"** once step 1 is verified — it imports the URL-prefix property and its sitemap without a separate verification step. Still current in 2026.
4. *(owner action, optional, low-cost)* Wire up **IndexNow**: generate a key, host `{key}.txt` under `/audio-blackbox/` (not the domain root — you don't control that), and submit URLs to `https://api.indexnow.org/indexnow` with the `keyLocation` parameter pointing at that sub-path file. This is valid under IndexNow's "Option 2" and, because every URL you'd ever submit is already under `/audio-blackbox/`, the sub-path restriction costs nothing.
5. *(code change, separate issue if pursued)* A `pages.yml` step that pings IndexNow's endpoint (Bing + Yandex share the index) after each successful deploy. Optional, not required for baseline indexing — pull/push crawling will find you via the sitemap regardless.
6. *(owner action, out of this repo)* Do **not** bother adding a root `robots.txt` to the user-site repo purely for AI-crawler allowlisting — a missing robots.txt is already allow-all, so there is nothing to unblock. The one thing worth doing in that other repo, if the owner ever touches it, is adding `Sitemap: https://alexandre.machado.cc/audio-blackbox/sitemap.xml` to a root `robots.txt` — but this is redundant with directly submitting the sitemap to GSC/Bing (step 2/3) and is not worth a special trip to that repo on its own.
7. *(code change, low priority)* Replace `docs/indexação.md`'s `WebApplication` JSON-LD example with `SoftwareApplication` (or the more specific `MobileApplication`), since the site is a landing page for a native Android app, not a web app. Include `operatingSystem: "ANDROID"`. Google's rich-result eligibility additionally wants `offers.price` and a rating/review — the owner should skip those rather than fabricate a price or reviews the app doesn't have; the JSON-LD is still valid, legible structured data for LLMs even without rich-result eligibility.
8. *(owner action)* AI-crawler robots.txt decisions don't need a *repo* change at all right now (see finding 3) — but if the owner ever authors that root `robots.txt`, decide training vs. retrieval/citation crawlers separately (see finding 4): allow `GPTBot`, `ClaudeBot`, `CCBot`, `Google-Extended` for training only if comfortable with GPL-licensed doc text being used as model training data (it's a defensible "yes" for an OSS project trying to be known); always allow `OAI-SearchBot`, `ChatGPT-User`, `Claude-User`, `Claude-SearchBot`, `Googlebot`, `Bingbot` since blocking those directly reduces citability, which is the whole point of this issue.
9. *(owner action)* Backlinks: list the app on the **GitHub repo's own "About" panel URL field and topics** (already low-cost, directly crawled by GitHub-adjacent bots and by `CCBot`/`GPTBot` since GitHub itself is heavily represented in Common Crawl); consider an **F-Droid** submission only after confirming the app has zero Google Play Services/Firebase dependencies (not confirmed either way in this pass — see gaps); a single, technically-substantive **Show HN** post is fine per HN's own guidelines, framed as "I built X," not a sales pitch. Skip Reddit/dev.to/Medium mass-posting — the evidence found supports single honest posts, not the multi-forum blitz `docs/indexação.md` suggests.

### Findings

**1. Search Console property type**
- **Domain property requires DNS TXT verification exclusively; URL-prefix property supports HTML file, meta tag, GA, GTM, or TXT.** [verified] — Search Console Help, "Verify your site ownership," https://support.google.com/webmasters/answer/9008080?hl=en. > "Domain properties... you must have access to the DNS configuration of your domain... URL-prefix properties... can be verified in a variety of ways."
- **A sitemap submitted through Search Console is not limited to its filesystem location; a sitemap posted elsewhere without GSC submission only covers descendants of its own directory.** [verified] — Google Search Central, "Build and submit a sitemap," https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap. > "a sitemap posted at the site root can affect all files on the site, which is where we recommend posting your sitemaps" and sitemaps affect "descendants of the parent directory" unless submitted via Search Console.
- **Project sites without their own custom domain are served as a sub-path of the user site's custom domain** — this is exactly this deployment. [verified] — GitHub Docs, "About custom domains and GitHub Pages," https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages. > "if the custom domain for your user site is www.octocat.com, and you have a project site with no custom domain configured... the GitHub Pages site for that repository will be available at www.octocat.com/octo-project."

**2. Bing Webmaster Tools**
- **"Import from Google Search Console" still exists as a documented flow and auto-verifies the imported site**, avoiding a separate Bing verification step. [reported, from a secondary summary, not the Bing help page itself — Bing's own help page returned no readable body when fetched] — sources describing the current flow: Bing's blog post on the feature (2019, mechanism unchanged per multiple 2026-dated third-party guides) and current third-party walkthroughs; I could not get a clean fetch of `bing.com/webmasters/help/add-and-verify-site-12184f8b` (returned only a page title, no body — likely JS-rendered). **This sub-finding is weaker than the others; treat as assumed pending the owner clicking through the actual Bing UI.**
- **IndexNow key files can live under a sub-path, not just the host root, via the `keyLocation` parameter — and a sub-path key file's authority is scoped to that same sub-path**, which matches this project exactly. [verified] — IndexNow.org, "Documentation," https://www.indexnow.org/documentation. > "A key file located at http://example.com/catalog/key12457EDd.txt can include any URLs starting with http://example.com/catalog/ but cannot include URLs starting with http://example.com/help/."

**3. The apex `robots.txt` question**
- **A missing robots.txt is treated as allow-all** — this is standard robots.txt semantics, not specific to this site; no crawler is blocked today. [assumed — this is the universally-documented default behavior of the Robots Exclusion Protocol, not something I found a single fresh 2026 doc restating, but it's uncontested basic behavior].
- **A root robots.txt CAN declare a `Sitemap:` line pointing at a sitemap hosted under a different path on the same host.** [verified] — Google Search Central sitemap doc (same URL as above). > format example given: "Sitemap: https://example.com/project/sitemap.xml" is valid inside a root-level robots.txt.
- That root `robots.txt`, however, lives in the **user-site repo** (`alexandre-machado.github.io`), not in `audio-blackbox` — this repo genuinely cannot serve it, confirmed by the GitHub Docs project-site behavior above. Whether creating one is worth a special trip to that other repo is a judgment call: given that directly submitting the sitemap to GSC and Bing (findings above) achieves discovery without touching the other repo, the marginal benefit of also adding a `Sitemap:` line there is low. [speculative — my own inference weighing effort vs. redundant benefit]
- **Apex 404 costing "domain-level trust":** no evidence found either way. [insufficient public evidence] — I did not find an authoritative source stating that a 404 at an unconfigured Pages root measurably harms a *different, live* sub-path's ranking. Google's crawlers evaluate URLs largely independently; a dangling apex is common and unremarkable for personal domains that host their real content under a project path.

**4. AI crawler tokens**
- **`Anthropic-ai` / `anthropic-ai` are not current tokens.** Anthropic's official current crawlers are `ClaudeBot` (training), `Claude-User` (on-demand fetch when a Claude user asks about a URL), and `Claude-SearchBot` (search-result indexing). [verified] — Anthropic/Claude Support, "robots.txt and Claude crawlers" (redirected from support.anthropic.com to support.claude.com), https://support.claude.com/en/articles/8896518. > confirms three tokens (ClaudeBot / Claude-User / Claude-SearchBot) and explicitly that "Anthropic-ai" is not a current documented token.
- **`Google-Extended` is a robots.txt *control token*, not a fetching user-agent** — it governs whether content already fetched by Googlebot is eligible for Gemini training and grounding (including grounding in Gemini Apps), and separately does **not** affect Google Search ranking/indexing. [verified] — Google Search Central, crawler overview (via search-result synthesis of the same official page family used above — Google's "google-common-crawlers" documentation lists Google-Extended's purpose distinctly from Googlebot's). > "Google-Extended... does not impact a site's inclusion in Google Search nor is it used as a ranking signal," and covers "future Gemini model training, grounding in Gemini Apps, and grounding in Google Search on Vertex AI."
- **OpenAI has three independently-controllable tokens: `GPTBot` (training), `OAI-SearchBot` (ChatGPT Search indexing), `ChatGPT-User` (fetch on a live user request).** [verified] — OpenAI Developers, "Overview of OpenAI Crawlers," https://developers.openai.com/api/docs/bots. > "Disallowing GPTBot indicates a site's content should not be used in training generative AI foundation models," and "Sites that are opted out of OAI-SearchBot will not be shown in ChatGPT search answers," and ChatGPT-User activates "When users ask ChatGPT... it may visit a web page."
- **Training vs. retrieval genuinely are separable decisions and every major vendor now supports setting them independently** — confirmed structurally by all three vendor docs above (Google: Googlebot vs Google-Extended; OpenAI: GPTBot vs OAI-SearchBot/ChatGPT-User; Anthropic: ClaudeBot vs Claude-User/Claude-SearchBot). `docs/indexação.md`'s flattened list (treating `Googlebot`, `Google-Extended`, `Bingbot`, `GPTBot`, `ChatGPT-User`, `OAI-SearchBot`, `Anthropic-ai`, `CCBot` as one undifferentiated "allow all of these" block) misses this distinction and uses a wrong/deprecated Anthropic token.
- **`CCBot` (Common Crawl)** is a training-data crawler feeding many downstream models' pretraining corpora, not a live citation mechanism for any specific assistant. [assumed — well-established public fact about Common Crawl's role, not re-verified against a fresh Common Crawl doc this session since it wasn't decision-relevant enough to spend budget on].

**5. Backlinks / external authority**
- **F-Droid requires the app and all its dependencies to be FOSS**; proprietary libraries including Firebase and Google Play Services are explicit disqualifiers. [verified] — F-Droid, "Inclusion Policy" / "Contribute," https://f-droid.org/contribute/ and https://f-droid.org/en/docs/Inclusion_Policy/. > app must be FLOSS, "should only have FOSS dependencies," and "Firebase and GMS are notable examples of non-FOSS libraries that are not accepted." **I checked `app/build.gradle.kts` in this repo for `firebase`/`com.google.android.gms`/`play-services` and found no matches — but I did not do a full dependency-tree audit, so this is not a green light, just "nothing obviously disqualifying found."**
- **Hacker News's own guidelines permit self-posting, including Show HN, as long as it isn't purely promotional and isn't the account's primary activity.** [verified] — Hacker News Guidelines, https://news.ycombinator.com/newsguidelines.html (content corroborated via direct quotes surfaced in search results from that same page). > "Please don't use HN primarily for promotion... Show HN can't just be pure promotion — keep it light, keep it interesting," and don't solicit upvotes/comments.
- **GitHub repo "About" URL + topics field**: not independently verified against an official doc this session (this is standard, uncontroversial GitHub repo metadata usage, not a claim needing a citation beyond GitHub's own repo-settings UI, which I did not fetch given budget). [assumed — low-risk, well-known GitHub feature].
- **Reddit / dev.to / Medium mass-posting**: I did not fetch each platform's individual self-promotion policy (would have consumed several source-budget slots for low decision-relevance); `docs/indexação.md`'s "divulgue... em fóruns" is generic marketing advice, not evidence-backed, and I did not find or look for data quantifying its effect on AI-citability specifically. [insufficient public evidence for the multi-forum claim; treat that item of the doc as speculative/unverified].

### Implications for the decision

- **Search Console:** URL-prefix property, not Domain property. This is the one that matches what the owner controls and what needs verifying (a page under `/audio-blackbox/`), and it accepts a sitemap submission directly regardless of where that sitemap physically sits.
- **Bing:** Import-from-GSC remains the lowest-effort path; treat as assumed pending a manual UI check since I could not fetch Bing's own help page cleanly. IndexNow is a real, low-cost win specific to this deployment because the sub-path key-file restriction (Option 2) matches this project's URL space exactly — this is worth a `pages.yml` step if the owner wants near-real-time Bing pickup, but is not required for baseline indexing.
- **Apex `robots.txt`:** skip it. There's nothing to unblock (missing = allow-all) and the `Sitemap:` line benefit is redundant with directly submitting to GSC/Bing. Not worth a special trip into the user-site repo. No evidence either way on the apex-404-hurts-trust question — flagged as a genuine unknown, not a reason to act.
- **AI crawlers:** `docs/indexação.md`'s crawler list needs two corrections: drop `Anthropic-ai`, use `ClaudeBot` / `Claude-User` / `Claude-SearchBot`; and stop treating training and retrieval as one decision — the owner can (and per this evidence, arguably should) allow all *retrieval/citation* bots (`OAI-SearchBot`, `ChatGPT-User`, `Claude-User`, `Claude-SearchBot`, `Googlebot`, `Bingbot`) unconditionally since blocking them directly defeats this issue's goal, while treating *training* bots (`GPTBot`, `ClaudeBot`, `CCBot`, `Google-Extended`) as a separate, optional call. Moot right now regardless, since there's no robots.txt to author in this repo.
- **Schema.org:** `docs/indexação.md`'s `WebApplication` example is wrong for a native Android app landing page, confirmed — `SoftwareApplication`/`MobileApplication` with `operatingSystem: "ANDROID"` is the documented fit. Don't add `offers.price` or ratings the app doesn't have just to chase Google's rich-result eligibility bar; that's optional and fabricating either would violate the "don't misrepresent" constraint.
- **Backlinks:** GitHub About/topics and a single honest Show HN post are evidence-backed, low-risk. F-Droid is plausible but gated on a dependency check not completed here. Multi-forum posting (Reddit/dev.to/Medium) is not evidence-backed for this decision and reads as generic advice from the Gemini-authored doc rather than a sourced claim — deprioritize it.
